## 与预登记的偏差（如实记录）

1. **第一次运行有 bug，作废重跑。**
   - **原因：** FlashPrefill 的注意力后端会全局替换 sdpa。它在缓存之后处理多 token 片段时没有用因果掩码，teacher-forced 的答案片段因此能看到后面的 token。
   - **后果：** 所有条件都受影响，BF16 的 150 个 target 全部判错。
   - **处理：** 修正了 `attention.py`：多 token 解码片段改用以缓存末尾对齐的因果掩码，单 token 解码不受影响。然后整批重跑。
   - **没有提前看结果：** 发现问题时只看了 BF16 的正确数，没看任何 AUC。旧日志保存为 `run_before_mask_fix.log`。
   - **只影响本批：** 第一到第六批要么逐 token 解码，要么没有加载这个后端，都不受影响。
2. **预登记文本有一处笔误。** 判定 1 写成"4 个权重压缩条件"，实际只有 NF4、RTN4、Wanda 三个。下面按"三个中至少三个"判定；按原文"4 个中至少 3 个"读，结论也相同。

## 次要和探索性结果

### 分数据源的压缩后 lo AUC

| 条件 | HDFS | 路径在前清单 |
|---|---|---|
| NF4 | 0.80 | 0.59 |
| RTN4 | 0.76 | 0.67 |
| Wanda | 0.81 | 0.70 |
| FlashPrefill | 0.81 | 0.37 |

- **同一数据源（HDFS）上推广得很好：** 留出集 AUC 0.76–0.81，略高于开发集。
- **换到新格式就变弱：** 清单上只有 0.59–0.70，固定的检索头未必是清单任务的检索头。

### FlashPrefill

- 只有 10 个翻转，压缩后 lo 的 AUC 是 0.62 [0.39, 0.87]，不显著。
- 在 HDFS 上是 0.81，在清单上是 0.37。
- 它的 gap 下降量 AUC 0.71，上下文 NLL 上升 0.70。它是稀疏预填充，机制可能与权重压缩不同，样本太少，下不了结论。

### 只用 BF16 的两个量

两者都没有稳定推广：
- BF16 lo：0.49–0.58；
- BF16 分叉 margin：0.53–0.72，只在 RTN4 上显著。

开发集上 BF16 lo 的 0.71–0.74 偏乐观。

### 其他

- **全局指标在 NF4 上 AUC 显著低于 0.5：** 上下文 KL 0.31。可能是数据源混杂造成的：清单 prompt 的上下文 KL 更高，但翻转更少。不作解读。
- **gap 下降量随长度的变化：**
  - Wanda 再次随长度增大：0.48 → 1.76 → 2.52，与开发集一致。
  - NF4 和 RTN4 不单调。
  - 留出集里 32K 混入了清单，长度比较受数据源干扰。

## 结论

1. **主要判据在留出数据上成立：** 检索头上压缩后的 gold 对数优势，对三种权重压缩的翻转 AUC 为 0.71–0.75，同一数据源上 0.76–0.81。困惑度和 KL 类全局指标接近或低于 0.5。这可以作为论文的核心指标。
2. **"压缩前就能预测哪些 target 易损"不成立：** BF16 lo 在留出数据上接近随机，第六批的结论要撤回。论文里只能说，压缩之后测到的检索头对数优势能解释翻转。
3. **推广到新的数据格式时会变弱：** 检索头是在 HDFS 上选的。要推广到其他任务，可能需要按任务选头，或者聚合多个头。
4. **log n 关系方向一致，但幅度变弱：** 斜率从 −1.13 变为 −0.60。理论图像是定性支持，不能当精确定律写。

## 局限

- 每组只有 50 条 prompt，翻转数 10–50 个，区间宽。
- HDFS 原始日志只有约 2000 行，留出集与开发集的窗口有重叠，不是完全独立的数据。
- 只测了一个模型，Qwen2.5-7B-Instruct。
